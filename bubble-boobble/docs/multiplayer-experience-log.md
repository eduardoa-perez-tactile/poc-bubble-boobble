# Multiplayer implementation experience log

Evidence recorded during the implementation on 20 October 2026. This is a draft for the user to review; no Slack message has been sent.

## Office Arcade guide and release tooling

- **Expected:** read the live guide and use its managed engine server contract. **Observed:** the guide is reachable from the shell on the current office/VPN connection, while the web retrieval tool cannot access the internal hostname. Shell HTTP was a sufficient read-only fallback. The live guide documents `list_games`, `prepare_publish`, `publication_status` and `check_game`; read-only `list_games` returned `snake-engine` and `curvecoaster`.
- **Expected:** build the Linux authoritative export locally or on existing CI. **Observed:** the current host is Darwin arm64 and the 0.1.15 builder rejects cross-target exports with `E_CROSS` before compilation. No Docker/Podman/Colima/Orb is on PATH. The game repository has zero registered self-hosted runners. Engine repository runner inventory returns HTTP 404, so no access was assumed. **Follow-up:** inspected the official public Linux runtime archive and established the prebuilt production-host path below. No substitute simulation server was created.
- **Expected:** locate matching Linux distribution. **Observed:** `tactilegames/game-engine` release v0.1.15 has only `SHA256SUMS.txt`, but `tools/release/identity.mjs` points to the actual distribution repository `tactilegames/game-engine-releases`. That release includes a Linux x64 archive and Linux native SDK. **Guide improvement:** link the distribution repository and explain SDK versus full-source server build prerequisites explicitly.
- **Expected:** matching source revision guarantees client/server compatibility. **Observed from source:** `session.rs::refresh_mp_build` uses project version plus the running script's bundle hash; `open_project_assets_as` reads `gameengine/bundle.js` from cooked content. Platform exports have different texture/content hashes. **Action:** release verification compares actual cooked script bytes and project game/version/multiplayer config, then independently checks clean source/engine provenance. No build identity override is used.
- **Expected:** existing browser export customizations survive arcade packaging. **Action:** `arcade:build-web` invokes the existing `tools/web/toolchain.mjs export` with release config. The verifier requires its splash, player assets and `playtest-build.json` provenance. Static packaging alone does not prove touch controls in a browser.
- **Tooling evidence:** `npm run arcade:test` passes fifteen pure Node tests covering GPAK block extraction, platform/executable rejection, altered artifact/dirty source/engine/script mismatch, unsafe export paths, ZIP layout/checksums JSON-RPC error handling and build-flag restoration after failure. Fixtures exercise file validation only; no test claims to be a runnable game/server.
- **Game integration pitfall:** the existing web build hook writes `WEB_BUILD=true`, while the server direct cook normally sees the false default. Even though that flag is presentation-only, its differing bundled JS changes the engine match identity. The Linux wrapper now captures the same browser release flags during cook and restores the original afterward; exact artifact comparison remains required. Actual cross-platform exports have not yet been compared.
- **Linux distribution inspection:** downloaded the official archive into ignored local scratch and verified SHA-256 `4fce0275d3c9616238255e09403c24c897ee0efa605d96bfdc0d4d829b97a5d5` against the release checksum file. The archive carries a real no-protocol production V8 desktop host (`v8,desktop,shipped`) with match-server support and its WebGPU library. ELF symbol inspection found maximum glibc requirement 2.34, below arcade glibc 2.39. No Linux executable ran on the Mac.
- **Guide/CLI gap and concrete workaround:** installed `build server` always rejects with `E_CHECKOUT` even when its runtime contains the required production host. Added a checksummed-runtime exporter that uses the actual engine CLI release cook and copies that unmodified host/library into the builder's server layout, with matching `server.json` and provenance. Added a GitHub-hosted Ubuntu24.04 workflow triggered only by pushes to `codex/online-wave-survival` or explicit manual dispatch that uses public distribution access only, verifies real target library resolution/startup/socket upgrade and uploads a permission-preserving server TAR. The [actual Ubuntu24.04 run](https://github.com/eduardoa-perez-tactile/poc-bubble-boobble/actions/runs/39433292713) succeeded on source `d3048539129a3b1574fef50744c0be5f8a0d3d26`; its server job took 35 seconds. Official runtime download, release cook, actual authoritative cooked-game loading, library resolution, WebSocket upgrade and server TAR upload all passed. This proves the Linux export path at that revision, not a paired browser release or browser gameplay. **Suggested engine fix:** teach `build server` to select the official no-protocol prebuilt host, as desktop release builds already do, and test that path in Linux distribution smoke coverage.
- **Release review hardening:** browser builds now require the requested engine-root to resolve to the actual exporter toolchain directory before build/stamp and validate that checkout. Runtime receipts require exactly host/GPU/cooker SHA-256 keys, rejecting omitted, malformed or path-traversal entries. A mocked publication-contract test proves the engine `prepare_publish` request contains only `{slug, multiplayer: true}`.
- **Source identity tooling correction:** the clean source checkout at tag `v0.1.15`/commit `f4334da17701bf419fabae9f806d9e34edd947b0` still has tracked `engine-version.json` value `0.1.9`; release staging rewrites distribution metadata. The initial verifier wrongly treated that source field as release authority. It now derives the version from the exact clean `vX.Y.Z` Git tag, records the lagging field separately and leaves the source checkout unchanged. The existing exporter independently checks that tag against the installed SDK version. A regression test verifies both the valid lagging case and rejection of tracked modifications. This was our release-tooling assumption, not a multiplayer defect.
- **Cross-export identity failure and fix:** actual clean web/Linux exports at game revision `a915d3a` failed exact cooked-script comparison despite matching game and engine revisions and generated browser flags. The web script contained the `__GAMEENGINE_SYSTEM_SOURCES__` map; the installed Linux runtime omitted it. The source bundler enables transpiler source metadata when engine crates exist, while the installed runtime without a ready native SDK disables it. `GAMEENGINE_NATIVE_SYSTEMS=off` alone does not suppress that metadata. All arcade web/source-server/prebuilt-server wrappers now share a build environment that forces both `GAMEENGINE_TRANSPILE=off` and `GAMEENGINE_NATIVE_SYSTEMS=off`, overriding inherited values so both ship identical stock TypeScript. Pure bundling of the same scratch game using full-source and public-runtime CLIs produced byte-identical 3,745,111-byte scripts, SHA-256 `86592386670aa8d0758ae79a51ca5a08fc279b38820f74fab501a79084d4163b`. This proves the root cause and bundler alignment; rebuilt actual exports must still pass the existing verifier. No script/hash replacement or identity override is used. **Guide improvement:** explain that automatic transpiler metadata can change the whole-script identity between source and installed distributions even when native acceleration is disabled.
- **Publication:** not requested or performed. No Office Arcade `prepare_publish` call or game upload occurred, and no infrastructure was provisioned. GitHub artifact upload succeeded as part of the Linux job. A paired release ZIP and deployed browser acceptance remain separate gates.

## Gameplay and engine network evidence

- **Architecture:** fixed real-time authoritative input sync. The game always has ten occupied courtyard slots; the actual match seat count controls the human prefix, with deterministic companions filling the remainder. Full u64 decimal seeds survive initialization through BigInt, including values above JavaScript number precision.
- **Input/UI:** added room entry and human count, invitations, assigned dragon identity, local menu, reconnect feedback and results. Browser gameplay keys, touch and pad inputs are suppressed and released while an online menu is open, with a neutral/release requirement before resuming. Physical controllers and actual browser gameplay remain unverified. Eleven pure browser-control tests pass.
- **Engine harness gap:** `net test` drives rollback inputs without setting `multiplayer.match()`, so it would leave this integration on the title screen. Authoritative `mp test` is the relevant gate. Its recorded `online.assert-active` cheat fails unless ten dragons are active, the human/AI roster matches the seat count and gameplay shots have occurred. Release builds exclude the cheat.
- **Final network correctness:** all four cases in `.gameengine/multiplayer-evidence/summary.json` passed the authoritative harness with active-gameplay assertions, correct ten-dragon human/AI rosters and no divergence/desync. Together they compared 110 hashes. The table records final measurements on the local macOS arm64 host; latency/jitter are simulated frames, not milliseconds. Stalls are the engine-reported aggregate counts and remain a performance limitation.

- **Network performance limits:** final server timings exceed the engine's roughly 2 ms rollback guidance, particularly mixed AI under high jitter. All cases reached rollback depth 12; the two-human case averaged 443.5 rollbacks and 5,184.5 resimulated frames per player. Reported corrections were zero in all four cases. Measured wire traffic ranged from 2.11–2.21 kB/s upstream and 1.93–3.23 kB/s downstream per player. Passing hash agreement does not establish smooth internet play or mobile thermal/GPU performance.
- **Measured optimization:** on this macOS arm64 host, the initial ten-human 600-frame run reported 4.33 ms/server tick and 3.37 ms/client frame; removing repeated simulation draw-plan work reduced a subsequent same-shape run to 1.65 and 1.07 ms. These are local harness timings, not phone frame-rate or thermal claims. The longer/high-jitter runs include many prediction-window stalls, which must be reported alongside successful hash agreement.
- **AI state cost:** a mixed-AI run exposed repeated JSON serialization of the same navigation graph per bot. Online state now stores each immutable graph generation once, with per-slot indices; simulation restores and compacts references around the unchanged gameplay step. Equivalence tests compare normal and compacted paths through incremental graph construction, downing, shoes, boss transitions and JSON snapshot decode. Offline state format and behavior remain unchanged.
- **Presentation/performance:** online pool allocation uses conservative shared capacity bounds, stored in a rollback-owned document; stable capacity skips full draw-plan generation and pool scans. Tests cover actor plans and full courtyard scenes at window extremes. Local cue playback has a presentation-only cursor; rollback cannot replay heard SFX. Shared music is reasserted through the documented sim event: host audio drains after rollback and its mixer deduplicates the currently playing track. This avoids skipped music transitions during catch-up without undocumented APIs.
- **Lifecycle limitations verified in engine source:** unexpected socket loss retains a reclaim token, but explicit leave invalidates it; the last disconnected real-time room closes and server restarts lose live matches. Missing inputs repeat the last controls, including after abrupt disconnect. Best-effort local release is implemented, but neutral remote input or automatic AI takeover is not promised. Welcome exposes no complete current roster, so waiting UI labels observed connections rather than an exact occupancy count. Escape-menu input lacks a presentation API; the visible MENU button is supported.
- **Completed regression evidence:** the initial offline baseline was 272 passing tests; the final native V8 T0 run passed all 283 tests while preserving the recorded offline baseline hashes. The phone-low selection passed 12 tests on the engine host, and native V8/WebAssembly parity passed 11 tests per lane with zero mismatches. These phone-low settings ran on an Apple M2 Max/Metal host, not a physical low-end phone. Hermes is unavailable in the installed Mac SDK.
- **Render and release gates:** the full logic/render pass exposed one intentional mode-card golden change for the new Online entry; inspected and refreshed desktop/mobile references pass focused reruns. Recorded pipeline counts are 10 compat, 16 desktop and 10 mobile; the final mobile structural result is 9 draws against a limit of 14 and the full desktop result is 11 against 14. The latest installed-SDK `gameengine check` passed typecheck, validation, desktop cook and a 600-frame cooked smoke, but reported material program `7946469ed20397e0` as stale. Investigation found the installed distribution omits `crates/gameengine-render/src/materials/*.gen.json`; the full exact source checkout contains that valid hash in `standard.gen.json` at line 144. Recapturing does not repair this checker-data omission. The direct full-source CLI `pipelineIssues` check returned `ok: true` with `issues: []`, without a bypass. Use that matching source CLI for the genuine release gate; do not delete the valid record. **Suggested engine fix:** include built-in material program metadata in the installed SDK checker, or supply its equivalent from the distribution.
- **Full render suites and exact baseline comparison:** the combined mobile-tier run in `.gameengine/online-final-full-suite.json` completed 332 cases: 321 passed and 11 failed. A clean checkout at pre-feature revision `48cb9a7` reproduced the mobile T1 baseline in `.gameengine/pre-multiplayer-mobile-render.json`: 48 cases, 37 passed and the same 11 failed. Comparing failed test names and the first error line yielded an exact match, so this run added zero mobile render failures; the combined suite is still not wholly green. The full desktop-tier suite in `.gameengine/online-final-desktop-suite.json` passed all 332 cases and its 11-draw structural check. These suite totals predate the four added lifecycle-review tests.
- **Lifecycle review follow-up:** independent review found that starting a new room from results could retain the previous snapshot, and a closed transport could leave `multiplayer.match()` alive, allowing the local simulation to keep stepping. The UI path now resets result state, caches the reclaim token before best-effort leave and explicitly leaves the closed match. Reclaim remains best effort while other peers keep the room alive. The focused lifecycle selection passed 16/16 on desktop and 16/16 on mobile, including the four new review tests (`.gameengine/online-ui-lifecycle-desktop.json` and `.gameengine/online-ui-lifecycle-mobile.json`). These are code-level engine checks; browser reconnect remains unverified.
- **Browser acceptance:** deferred under `PROJECT.md`, which permits browser automation only when the user explicitly requests that specific action. Engine UI screenshots, file checks, parity and a server socket upgrade do not prove two actual browser players or ten-browser capacity. No browser automation or standalone desktop game playtest was used.
